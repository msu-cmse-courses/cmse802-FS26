# Final Project Code Review - Day 1

This begins a two-day deep review of the release-candidate project. The same review group stays together for Days 22 and 23 so reviewers can understand the project well enough to give specific, useful feedback.

## Agenda (80 minutes)

1. 5 min - Check-in, form review groups, and assign Day 1 roles
2. 10 min - Instructor overview: release-candidate expectations and deep-review protocol
3. 50 min - Deep review blocks: author walkthrough, independent checks, and evidence-based feedback
4. 10 min - Author response and prioritized fix plan
5. 5 min - Share the most important finding and prepare to switch roles on Day 2

### Learning Goals

By the end of this class, you should be able to:

- run a teammate's release-candidate project from a fresh clone and report what you observed; and
- give evidence-based feedback after seeing both the intended workflow and an independent attempt to run it.

## Group Peer Review

Work in the same pair or triad for both days. Each reviewer clones the author's repository into a new folder, follows only the README, and completes the [Quick Peer Review Form](../Guide/21-Peer-Review-Quick-Form.md). The goal is reproducibility evidence, not grading, so record exactly which command succeeded, failed, or was ambiguous.

### Role plan

- **Pairs:** On Day 1, Student A is the author and walks Student B through the project. Student B then performs independent checks and records evidence. On Day 2, Student B is the author and Student A reviews.
- **Triads:** Use timed review blocks. In each block, one student is the author, one is the execution reviewer who runs the documented workflow, and one is the documentation reviewer who traces the README, tests, handoff notes, and SPRRL evidence. Rotate roles so every student presents a project and serves in both review roles across the two days.

The author may explain the research context and intended result, but reviewers should still attempt the documented workflow independently before giving feedback.

Review focus:

- Can I set up and run the main workflow from the README alone?
- Is the project purpose, main result, and intended audience clear?
- Do the tests or validation checks run, and is a passing result recognizable?
- Does the repository provide a shareable synthetic, example, or mock workflow if the real data are restricted?
- Does the release-candidate handoff note accurately describe what is ready and what remains?

## Fix Your Own Repository

Turn the review evidence into a short, prioritized fix plan. Start the highest-priority fix if time permits, but keep the reviewer’s observed evidence and action items available for Day 2.

## Before Next Class

- Save and share the completed Day 1 review form with the author.
- Make progress on the highest-priority blocker, but preserve enough evidence for the Day 2 reviewer to understand the original issue.
- Bring your repository, fix plan, and review evidence ready to switch roles.
